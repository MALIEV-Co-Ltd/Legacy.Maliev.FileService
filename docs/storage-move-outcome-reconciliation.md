# Storage move outcome reconciliation

During scanned `POST /Uploads` promotion, the service can return an outcome-unknown `503` when a GCS copy or source deletion may have committed but its response was lost, canceled, or incomplete. The service deliberately retains the private quarantine object and any copied destination; it does not create clean `Upload` metadata or issue a signed URL for an unconfirmed promotion. Do not blindly replay the request or delete either object by name.

For `POST /Uploads`, the warning log records only the parent `operationId`. Use that identifier inside an access-controlled operator session to locate the quarantine prefix (`{QuarantinePrefix}/{operationId:N}/`) and correlate the durable idempotency checkpoint, if one exists. A separate PostgreSQL `StorageMoveJournal` row is written before each copy, keyed by the deterministic SHA-256-derived child operation ID for uploads (or a fresh operation ID for public `PUT /Uploads`). It records private source/destination coordinates, the generation returned by quarantine upload, the clean-scan flag, any acknowledged destination generation, and the last confirmed stage. Never put object names, which may contain customer filenames, into tickets, chat, or routine logs.

`SourceObserved` means the generation was journaled but copy may or may not have happened. `Copied` means the exact destination generation was acknowledged but source deletion is not confirmed. `SourceDeleted` means the copy and source deletion were acknowledged; metadata may still be absent or its commit response may have been lost. `MetadataCommitted` means the metadata write was acknowledged. `Unknown` preserves the earlier generation fields but requires operator investigation. A checkpoint update itself can fail after an external operation, so none of these stages alone authorizes a clean response. The journal has no time-based deletion or automatic promotion path.

The scanned POST path journals the uploaded quarantine generation before re-reading GCS. A missing or replaced live source is an unknown outcome, never a cleanup-eligible `false`. Before promotion, known scanner failures may clean only the exact uploaded quarantine generation through a conditional delete; a newer generation at the same name is not deleted. Once promotion is attempted or any outcome is uncertain, the service retains private objects for reconciliation.

Bounded operator reconciliation: read the journal row and matching `Upload` metadata in PostgreSQL, then read GCS metadata for the exact recorded generations and current live names. Confirm the destination generation belongs to the expected clean source and whether the source generation still exists; if the copied generation was not acknowledged, treat provenance as unproven until independent evidence establishes it. A newer source or destination generation is never a cleanup target. Record the decision in the controlled incident record. Only an independently authorized repair workflow may update metadata or conditionally remove an exact generation. This PR supplies evidence and fail-closed behavior, not an operator write command or automatic repair.

If clean metadata is absent, leave the checkpoint unknown and both storage locations private until an authorized operator establishes which generation is the scanned source, whether the copied destination exists, and whether either deletion committed. A `503` is not proof that a copy failed. Do not mark the workflow complete, issue a URL, or run a time-based/destructive cleaner solely because an object lacks metadata. Escalate uncertain ownership or generation changes rather than deleting a possibly newer object.

Current limitation: automatic `ReconcileUploadAsync` still requires both persisted clean metadata and a matching destination size. A move interrupted before metadata insertion remains unavailable for replay until operator disposition, and an unkeyed request has no durable HTTP replay identity even though its move journal survives. No direct GCS acceptance was run by this code path alone; validate generation behavior in an authorized disposable bucket before production rollout. This note does not authorize a production storage or database change.

If source deletion returns `404` after an acknowledged copy but its `SourceDeleted` journal update fails or is canceled, the move is also outcome-unknown. The service attempts the `Unknown` checkpoint with an independent two-second cancellation budget and does not issue another storage deletion. If that checkpoint also fails, the earlier `Copied` row and exact destination generation remain the last confirmed evidence; do not interpret `Copied` as permission to replay, sign, repair metadata, or remove either object. Controlled adapter and disposable PostgreSQL/controller tests cover both POST and PUT responses, request cancellation, and failure of the unknown checkpoint. These tests are not real-provider acceptance.

PR42 remains held until separately authorized disposable-GCS acceptance is complete. This checkpoint repair does not decide the parent issue13 signing-failure compensation policy, bind public PUT scan provenance to a metadata generation, cover lost initial quarantine-upload responses, or introduce automatic pre-metadata repair.
